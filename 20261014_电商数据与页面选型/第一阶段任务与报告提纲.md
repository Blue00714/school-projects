## 2. 当前选题与功能范围

题目：**基于FastAPI的智能电商运营管理系统设计与实现**。

应用场景：面向中小型电商商家的日常运营，辅助分析销售情况、预测短期销量、查看模拟补货场景和整理运营报告。开发与测试拟采用公开历史交易数据，不宣称已有真实商家部署。

第一版为单店运营后台，主要模块如下：

| 模块 | 功能与范围 |
|---|---|
| 用户与设置 | 登录退出；管理员维护账号和配置，运营人员使用业务功能 |
| 商品与订单数据管理 | Excel/CSV导入，字段与质量检查，商品和订单查询，导入批次及处理记录 |
| 运营分析 | 销售数量、销售额、订单数、商品排名、趋势及对比；取消记录单列 |
| 销量预测与回测 | 未来7天预测，简单基准与一个机器学习模型比较，历史时点回放及误差展示 |
| 模拟库存与补货辅助 | 模拟初始库存、出入库、采购提前期和安全库存；预警与待确认补货建议 |
| AI运营助手 | 自然语言查询，调用统计/预测/库存工具，展示范围及依据，生成报告 |

暂不加入用户画像、客服、营销策划、支付或自动调价。第一版训练对象为销量预测模型；AI助手通过已有模型接口调用工具，不预设另做大模型微调。

## 4. 前三章报告提纲

以下沿用模板章节结构，将示例中的学生成绩管理内容替换为本项目内容。

### 第一章 项目概述

**1.1 背景**：说明中小型电商运营中的数据分散、统计重复、短期销量判断及报告整理问题。以明确场景解释需求，不虚构商家访谈或调研结果。

**1.2 目的和意义**：统一交易数据、提供可核对的销售分析、比较短期预测方法、通过AI工具调用降低查询操作成本。收益提升与预测精度只作为待验证目标。

**1.3 研究和应用现状**：梳理电商运营后台、销量预测及Agent数据分析的代表性方法与系统。补充可核查来源，明确本项目侧重数据追溯、历史回测与辅助查询，避免宣称“填补空白”。

**1.4 本项目设计任务**：列明六模块、公开数据处理、模型比较、界面与数据库、AI工具调用、测试和报告交付，说明第一版范围。

### 第二章 项目可行性分析

**2.1 市场可行性分析**：按模板中的需求定位、目标用户展开。目标角色为商家运营人员与系统管理员；明确课程原型的使用价值，不写未经调查的市场份额或收益。

**2.2 技术可行性分析**：说明FastAPI接口、网页界面、数据库、数据处理、预测训练、模型API及工具调用怎样配合。说明现有开源组件与独立实现部分，列出需先验证的依赖。

**2.2.2 技术风险分析**：包括数据下载及缺失、商品销量稀疏、未来信息泄漏、API不可用或生成无依据内容，以及开发范围过大。对应提出范围限制、基准比较、时间切分、计算工具与人工确认。

### 8.1 顺序与验收

先核验数据，再做桌面商家后台页面原型；页面和接口约定后立即搭建FastAPI骨架。先跑通商品、订单和真实数据看板，再接预测、模拟库存与AI助手。最后做完整联调，FastAPI不留到最后才引入。

| 顺序 | 任务 | 本步验收结果 |
|---|---|---|
| 1 | 数据质量与预测可行性检查 | 核对两表交叠、重复、取消、缺失与时间覆盖；确定销量口径及实验范围。用一个简单历史基准做小验证，确认时间外回测可构造，不做完整调参 |
| 2 | 页面原型与接口约定 | 选定桌面商家后台风格，确定看板、商品订单、预测回测、模拟库存、AI助手页面及主要交互。原型示例数字标为占位，列出需要哪些接口字段 |
| 3 | FastAPI与数据库骨架 | 服务可启动，页面能请求接口；约定商品、订单、统计、预测和错误响应，建立来源、导入批次及任务记录 |
| 4 | 商品订单与真实数据看板 | 查询、筛选、分页、质量检查和图表使用核验过的数据；同一窗口人工核对销量、销售额和订单数 |
| 5 | 销量预测与历史回测 | 固定时间切分，比较近期均值、上周同日和一个机器学习模型；保存模型及结果，页面显示预测/实际曲线、MAE、WAPE与失败案例 |
| 6 | 模拟库存与补货提示 | 设置初始库存、采购提前期、安全库存和模拟出入库；库存变化可核对，预测驱动提示明确标为模拟 |
| 7 | AI运营助手 | 接入模型API，调用步骤4—6已有工具；支持参数追问、数据查询、解释和简报；数值与页面统计一致 |
| 8 | 联调、报告与答辩 | 跑通导入→看板→预测回测→模拟库存→AI报告的演示；整理错误/耗时测试、图表、依赖说明及答辩材料 |

步骤1的预测基准只判断数据与回测是否可用，完整训练在步骤5开展。若个别商品不适合预测，按事先说明的条件调整范围或改为全店记录销量；不能看过测试结果后只留下容易预测的商品。

### 8.2 功能怎样接入FastAPI

统计、预测和库存规则写成独立业务模块，先能单独运行和验证，再由FastAPI接口调用。FastAPI负责接收参数、校验、权限及返回结果，页面与Agent共用同一套业务计算，避免口径不一致。

流程为：页面或AI助手 → FastAPI接口/查询工具 → 业务模块 → 数据库或预测结果 → 返回图表与解释。

前端框架在页面选型后确定。若采用现成Vue电商前端，需要核实其接口适配工作量；若采用HTML模板，则沿用同一后端和数据口径。

### 8.3 微调与范围控制

此前讨论了电商查询与工具调用的SFT＋LoRA领域微调，尚未正式确定实施。若纳入，先在步骤7建立可用工具及未微调基准，再准备人工审核样本，评价工具选择、参数和数字一致性。是否改善以独立测试为准，训练损失下降不能替代效果验证。

先完成完整系统和销量预测实验，再结合训练样本、算力和课程时间决定额外微调实验。不同时启动多个训练项目。

维持六模块范围，不加入真实支付、购物前台、用户画像、客服、营销策划或自动调价。原始数据、预测结果和模拟库存分别标识；没有成本与访问记录时不展示真实利润、点击率或转化率。
